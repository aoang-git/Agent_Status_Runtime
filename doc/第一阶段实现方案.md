# Agent Status Runtime 第一阶段实现方案

研究日期：2026-10-22。状态：实施建议，尚未完成目标 Agent 的实机兼容认证。

> 实施顺序已按用户后续要求调整：先交付无需修改 Agent 配置的文件被动监测；Hooks 安装、信任和其他配置增强逐步适配。当前可运行范围与命令见 [README](../README.md)。下文原生 Hooks 内容保留为后续设计，不代表 v0.1 已实现。

## 1. 结论与范围

首期建议交付：**一个用户级 Go Runtime、四个 Agent 适配器、六种入口的独立能力声明、文件采集与可选原生 Hooks、本机 HTTP/SSE、诊断 CLI 和回归样本库。**

六种入口为 Codex CLI、ChatGPT 桌面版 Codex 模式、Claude Code CLI、Claude 桌面版 Code、本地 DeepSeek Harness、Pi coding agent。CLI 与桌面端共享解析代码，但不能共享一张未经验证的兼容性证书。

本方案延续 [原架构](agent状态统一监测项目架构.md) 与 [可行性研究](agent状态统一监测计划.md) 的核心约束：不接管启动、不控制任务、不代替用户审批、不保存对话正文；默认文件观察，允许知情配置原生 Hooks。此次需求将 DeepSeek 提前到首期，Qoder、OpenCode、Cursor、Copilot 后移。Claude/Codex Hooks 与文件源在首期内一起完成，不再等到第二阶段。

范围假设：桌面支持指**本地执行的编码会话**；Windows 是首个交付验证环境，核心保持跨平台，macOS/Linux 另列验证记录。远程主机、WSL、容器是不同执行环境，不因为桌面能打开会话就认为宿主机可读取其事件。云端专有接口仍遵循原文档的首期排除项。

成功标准不是“能显示六个品牌入口”，而是：能发现真实会话，给出有来源、时间和可信度的状态，遇到信息缺失正确降级，且不会将历史记录、旧回合、自动审批或进程退出误报为新任务成功。

## 2. 证据与需要修订的前提

本报告区分三类材料：官方文档/源码说明能力；社区 issue 提供故障与回归线索；参考项目提供实现思路。**任何一类都不能替代目标版本上的端到端测试。** 本次未运行模型任务、未安装 Hooks、未读取私人会话内容。

| 原方案容易产生的理解 | 本次核对后的实施口径 |
|---|---|
| 支持 CLI 就支持同品牌桌面版 | 分别记录产品版本、内核版本、执行环境、配置来源和样本结果 |
| JSONL 有工具调用，所以能精确判断正在执行 | 只证明记录存在；按事件语义区分调用意图、执行、结果 |
| PermissionRequest 就是人工等待 | 可能被其他 Hook/策略自动处理，人工等待必须单独确证 |
| Stop 或最终 assistant 文本就是完成 | 区分停止候选、实际回合终止、自动续跑、失败和业务目标完成 |
| 任意两个来源一致即可认证 | Hook 与 transcript 可能同源、同样漏发；需要检查终止语义与回合关联 |
| 所有 JSONL 都是线性对话 | Pi 存在会话树；Codex 新旧历史模式不同 |
| 压缩日志只能定期全量解压 | DeepSeek 可按完整 Zstd 帧增量读取，但需处理半帧及代际切换 |

原研究附录有失去 `://` 和 `/` 的链接，不能直接用作可追溯依据。本报告在各结论处提供重新核对的可访问来源；未将旧文档的勾选表当作已验证结果。

## 3. 接入方式选择

| 方案 | 优点 | 代价 | 首期选择 |
|---|---|---|---|
| 文件源 + 原生 Hooks | 符合既有启动习惯；覆盖现有会话；无需每款单独插件 | 需要版本化解析和降级，能力不完全对称 | 采用 |
| Agent SDK / App Server / RPC / Extension | 某些平台能提供更完整的实时生命周期 | 引入专用运行时、扩展安装或连接要求；未必能观察任意既有进程 | 保留后续评审，不混入首期 |
| 终端抓屏、标题正则、UI 自动化 | 能补少量可见提示 | 依赖主题、语言、焦点、tmux；桌面端差异大 | 不作为状态证据 |

Codex App Server 确实有线程状态与事件协议，但新启动一个服务器，不等于自动获得另一个 CLI/桌面进程的实时状态。官方文档描述的是加载线程和客户端订阅生命周期；因此这里不将其当作跨进程被动总线，也不通过 resume 观察用户会话。[官方 App Server 文档](https://learn.chatgpt.com/docs/app-server)

## 4. 首期能力矩阵

以下是**实施目标与证据上限**，不是认证结果。`直接`表示存在明确语义的事件，仍受版本、落盘和丢事件影响；`部分`表示有推断或覆盖缺口；`待验`要求该入口单独实测；`不承诺`表示当前方案缺少充分证据。

| 入口与来源 | 会话发现/活动 | 工具活动 / 真正开始 | 人工等待 | 回合终止/结果 | 首期定位 |
|---|---|---|---|---|---|
| Codex CLI：rollout + Hooks | 直接/部分 | 直接/部分 | 部分 | 直接但异常路径有缺口 | 标准适配器 |
| ChatGPT 桌面 Codex：本地/Worktree | 待验，复用 Codex 解析 | 待验 | 待验 | 待验 | 独立入口验收 |
| Claude Code CLI：JSONL + Hooks | 直接/部分 | 直接/部分 | 部分 | 部分，按停止/失败/中断区分 | 标准适配器 |
| Claude 桌面 Code：本地会话 | 待验，复用 Claude 解析 | 待验 | 待验 | 待验 | 独立入口验收 |
| DeepSeek Harness：持久化事件 | 直接，受批量落盘影响 | 直接/不承诺精确开始 | 部分 | 直接，必须解释 reason | 首期专用帧读取器 |
| Pi：持久化 JSONL | 部分 | 直接/不承诺精确开始 | 不承诺 | 部分 | 基础监测 |

不支持的能力返回 `unsupported`，尚未测试返回 `unverified`，源损坏返回 `degraded`。不要把三者合并成 false，也不要把不支持项计入准确率分母。

## 5. Codex CLI 与 ChatGPT 桌面 Codex

### 5.1 文件源

从已识别的 Codex 数据根目录及 Hook 的 `transcript_path` 发现 rollout；`~/.codex/sessions` 仅作为默认候选，不硬编码为唯一位置。来源元数据不足时，入口标记 unknown，不能凭 cwd 或进程名把 CLI 和 Desktop 合并。

官方源码区分 Legacy 与 Paginated 历史：保留回合开始、结束、中断；部分工具开始、审批、错误属于非持久事件，新历史使用 `ItemCompleted`。因此必须有格式识别和分别测试的解析分支，不能假定 JSONL 等于完整实时事件流。[持久化策略源码](https://github.com/openai/codex/blob/main/codex-rs/rollout/src/policy.rs)

原始协议中的 `task_started` / `task_complete` 与 `turn_started` / `turn_complete` 兼容标签应按目标版本样本验证；不要混用 App Server 的 `turn/completed` 名称。结束记录仍需检查结果及回合关联。[官方协议说明](https://github.com/openai/codex/blob/main/codex-rs/docs/protocol_v1.md)

### 5.2 原生 Hooks

候选订阅：`SessionStart`、`UserPromptSubmit`、`PreToolUse`、`PermissionRequest`、`PostToolUse`、`Stop`、`Interrupt`、`SessionEnd`，以及需要父子关联时的子 Agent 事件。用户级配置须合并写入；新增或变更定义需经过 Codex 信任审核。

`PreToolUse` 只进入工具活动；`PermissionRequest` 只证明请求产生；`Stop` 作为结束候选，防止其他 Hook 触发续跑；`SessionEnd` 不能代替每轮完成。转发器不返回审批、阻断或上下文注入字段。[官方 Hooks 文档](https://learn.chatgpt.com/docs/hooks)

### 5.3 桌面边界与社区证据

ChatGPT 桌面 Codex 的 Local 和 Worktree 在本机执行，Cloud 在独立远程环境执行；首期认证前两者。[官方环境说明](https://learn.chatgpt.com/docs/environments/modes)

还要区分执行位置与编排位置：云端编排即便使用本地工具，也不等于能运行本地 command hooks。该组合不自动继承本地模式能力。[官方 Hooks 的 managed/cloud 限制](https://learn.chatgpt.com/docs/hooks#managed-hooks-from-requirementstoml)

| 反馈 | 证据边界 | 转化为测试 |
|---|---|---|
| [#54884](https://github.com/openai/codex/issues/54884)：API 错误没有 Stop/Interrupt | 报告环境为 CLI 0.163.0、WSL2；本次访问显示 Open，不代表全版本都复现 | API 400、网络异常、鉴权失败；无终止证据只能 unknown |
| [#38972](https://github.com/openai/codex/issues/38972)：桌面后台状态与 rollout 活动冲突 | 用户报告，非官方协议承诺 | 迟到事件、后台线程、旧终止事件不得覆盖新活动 |
| [rollout 读取讨论 #45392](https://github.com/openai/codex/discussions/45392) | 社区对特定源码版本的分析 | 旧回合结束后新回合未结束、缺 turn ID、中途截断 |

这些证据支持“组合采集 + 保守状态机”，不支持承诺 Hooks 与文件源能补齐所有失败路径。

## 6. Claude Code CLI 与桌面 Code

### 6.1 发现与事件

默认从 `~/.claude/projects` 发现 transcript，优先使用 Hook 提供的实际路径，并支持额外用户数据根。CLI 与 Desktop 共用用户级 settings/Hooks，但桌面覆盖限定 Code 的本地会话，不扩展到普通 Chat/Cowork。[官方 Desktop 配置说明](https://code.claude.com/docs/en/desktop#shared-configuration)

候选事件为 `SessionStart`、`UserPromptSubmit`、`PreToolUse`、`PostToolUse`、`PostToolUseFailure`、`PermissionRequest`、`Notification`、`Stop`、`StopFailure`、`SubagentStart`、`SubagentStop`、`SessionEnd`；安装时按版本能力选择。

`Stop` 不覆盖用户中断；`StopFailure` 用于 API 失败。`PermissionRequest` 不提供 `tool_use_id`，不能虚构关联；`Notification(permission_prompt)` 有延迟，需结合后续活动处理迟到通知。Stop 仍可能被其他 Hook 延续，子 Agent 或后台任务结束也不能替代主回合结束。[官方 Hook 契约](https://code.claude.com/docs/en/hooks)

实施采用 Hooks 提供实时事实、文件负责发现与补偿。`PreToolUse` 归为工具活动；只有确证执行才标 `tool_started`。无法可靠识别用户中断或最终停止时返回 partial/unknown，不从 transcript 末尾文字推测。

## 7. DeepSeek Harness

### 7.1 发现与物理格式

默认 home 为 `~/.dsh`，`DSH_HOME` 或显式配置可改变位置；会话根目录另允许登记。发现流程按 home/root 而非某一个前端进程建立身份。[官方 home 解析设计](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/implemented/architecture/2026-07-24-single-harness-home-resolver.md)

持久化目录内选择数字最高的 canonical `session.vN.jsonl.zstd` 或 `.jsonl`；无版本后缀属于早期代际。当前主干格式常量为 v4，但文档示例可能仍是 v3，必须以受测版本 header 和类型定义为准。未知更高代际不能悄悄回退旧文件。[会话类型源码](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/packages/core/session/src/types.ts)

压缩存储是连续拼接的标准独立 Zstd 帧，带 checksum；头与后续 batch 分帧，并非自定义长度前缀容器。只提交校验通过的完整帧及游标；半帧等待，损坏报告 degraded，不替上游修复。[后端格式说明](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/packages/session/session-persistence-jsonl/README.md)、[帧实现](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/packages/session/session-persistence-jsonl/src/zstd.ts)

当前源码有 200ms 批处理等待上限，它不包括所有调度、磁盘和重试耗时，不能作为实时 SLA。[写入实现](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/packages/session/session-persistence-jsonl/src/storage.ts)

### 7.2 标准化映射

| 原始事件 | Runtime 处理 |
|---|---|
| `turn/start` | 当前回合开始 |
| `step/start` | 回合内部活动，不新建回合 |
| `tool/call` | `tool_observed`，保留 callId |
| `tool/result` | 工具结果与结束证据；不自动结束回合 |
| `approval/asked` | 审批请求候选 |
| `approval/decided` | 按审批 ID 清理 pending，包括拒绝/取消/不可用 |
| `turn/end` | 按 reason 分类，不按事件名一律完成 |

`tool/call` 位于审批和工具执行之前；`approval/asked` 是 answerer chain 审计，不一定出现人工弹窗。完整 batch 内先归并 asked/decided，再发布状态，避免自动审批闪烁成“等待用户”。[工具流水线](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/tool-execution-pipeline.md)、[审批实现](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/packages/interaction/user-approval/src/index.ts)

结束分类：`completed`→完成；`aborted`→中断并保留 cause；`error`→失败。建议将 `blocked`、`max-tokens` 归为 failed 并保留原原因，这是本 Runtime 的产品映射。`interrupted` 是恢复补写，`forked` 是 fork 合成闭合，不作为刚刚发生的新通知；未知原因→ended/unknown。[结束类型定义](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/packages/core/session/src/types.ts)

崩溃可能留下未闭合回合，恢复时才补写结束。本 Runtime 只观察，不能写入 closer，也不能把静默当作取消。[官方恢复说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/persistence.md)

### 7.3 风险验证

[Discussion #10601](https://github.com/deepseek-ai/deepseek-harness/discussions/10601) 报告 Windows snapshot 延迟回合结束；因此 assistant/step 已结束不能提前发完成。[#6875](https://github.com/deepseek-ai/deepseek-harness/discussions/6875) 报告旧格式 header 可读而 body 解析失败；因此“发现会话”和“可监测状态”必须是不同能力。均作为回归线索，未在本项目复现。

先认证一个明确的当前格式版本；旧代际只在有样本时支持。帧序号、事件顺序与代际参与去重，升级代际重建快照不重播历史通知。Windows 下读取共享和文件替换必须实测。

Fork 的继承前缀只用于建快照，不能当作 child 的新活动；按目标格式识别 seed 边界。fork 血缘也不自动等于运行中的子 Agent 关系。同一 root 按已知 encoding 读取，同代同时出现两种编码且无法确认权威文件时报告歧义，不按遍历顺序任选。[后端格式与 fork 说明](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/packages/session/session-persistence-jsonl/README.md)

## 8. Pi coding agent

上游 `badlogic/pi-mono` 已重定向至 `earendil-works/pi`，旧的单数 `docs/session.md` 链接不再是本次使用的有效文档路径。

当前 session 文档给出的默认目录为 `~/.pi/agent/sessions/`，支持目录覆盖与 `--no-session`。无持久化模式在首期文件方案下不可观察，能力声明标为 unsupported；缺乏其他发现证据时，也不承诺能列出该具体会话。[会话配置](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sessions.md)

JSONL v3 的 `id/parentId` 构成会话树。读取器需要维护分支关系，不能把末尾物理行之前所有消息拼成一条线性历史；分支选择无法确证时保留 unknown。[格式说明](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/session-format.md)

当前实现按消息结束持久化，主干首次 user/assistant 消息可触发建档，旧版本可能等待首个 assistant；后续重写也需按版本测试。这意味着文件记录不能直接提供流式工具开始或完整实时生命周期。[agent-session 源码](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/src/core/agent-session.ts)、[session-manager 源码](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/src/core/session-manager.ts)

关键区别：实时事件中的 `agent_end` 不等于 session-level settled，自动重试、压缩恢复或排队消息可以继续；`agent_settled` 才描述无自动后续工作的边界。它属于 JSON/运行时事件流，不能假设也持久化在 session 文件中。[官方 JSON 事件说明](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/json.md)

首期交付会话发现、近期活动、工具调用/结果证据、明确 message 结果的有限识别；**不承诺精确人工等待和 session-level 完成通知**。消息结束不能冒充整轮自动工作已结束。更完整支持可选 Extension，但属于未来范围变更，不能暗中安装。[官方 Extension 机制](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md)

[Issue #7350](https://github.com/earendil-works/pi/issues/7350) 记录通知示例使用 agent_end 过早提醒，已关联修复；[#10000](https://github.com/earendil-works/pi/issues/10000) 记录旧版本首个 assistant 前不落盘问题。当前源码已有变化，验收须覆盖旧样本并锁定最低支持版本，不把主干改动等同于用户安装版本已有修复。

## 9. Runtime 详细设计

### 9.1 最小实现结构

沿用 Go、SQLite、文件通知 + 补偿扫描、标准 HTTP/SSE。首期不开发 GUI、LAN 配对、自动更新和多语言 SDK。以下为拟建目录，不表示代码已存在：

```text
runtime/
  cmd/agent-statusd/       serve、status、doctor、hooks 管理
  internal/collect/        JSONL、Zstd、目录发现、游标
  internal/adapters/      codex、claude、deepseek、pi
  internal/state/         标准事实、会话/回合状态、去重
  internal/storage/       SQLite 快照、游标、事件日志
  internal/api/           本机 HTTP/SSE、受限 IPC
  tests/fixtures/         去敏样本与预期事件
  tests/compatibility/    真实版本/入口场景记录
```

适配器只处理发现、解析、来源语义及能力报告；状态机统一决定展示与通知。先编译期注册四个适配器，不实现动态插件加载。

### 9.2 统一事实与身份

复用原架构的 `turn_started`、`tool_observed`、`tool_started`、`tool_ended`、`approval_requested`、`approval_resolved`、`turn_ended`、`turn_interrupted`。必要时增加内部 `turn_end_candidate` 与 `human_wait_observed`，避免把弱证据升级为强事实。

每条事实至少含：

| 字段组 | 内容 |
|---|---|
| 来源 | agent、surface、environment_id、source、adapter_version |
| 身份 | 原生 session_id、可选 turn_id、tool_call_id、approval_id、parent_session_id |
| 时间/顺序 | occurred_at（可空）、observed_at、source_seq 或文件位置 |
| 语义 | kind、outcome、reason、confidence、是否历史回放 |
| 证据 | 原始事件类型与脱敏定位标识；不保留正文 |

会话唯一键采用 `(agent, environment_id, data_root_identity, native_session_id)`。surface 是属性，不能使同一原生会话在 CLI/桌面打开时重复计数。缺乏身份或父子关系证据时，不按项目目录相同强行合并。没有原生 turn_id 时分配本地回合序号并保存关联可信度。

### 9.3 状态与通知规则

1. 为每个回合维护工具集合、待审批集合和终止证据；并行工具不能只用一个布尔值。
2. 已证实人工等待优先于工具活动；纯审批请求只产生 inferred 候选，后续自动处理须清除。没有“审批已解决”事件时，关联工具后续活动只能作为推断，不能凭任意新事件清除全部等待。
3. 文件中的旧事件不覆盖新回合；缺少回合 ID 的迟到终止事件进入歧义诊断，不自动关闭当前回合。
4. 明确结束生成一次终止通知；`completed`、`interrupted`、`failed`、`unknown` 分开。失败不是正常完成，也不等于用户取消。建议统一 `turn.ended` 携带 outcome，并保留原架构的完成/中断专用事件。
5. Stop 候选不能因静默超时升级为确定完成。能拿到最终终止证据就确认；拿不到则保留候选或降为 unknown。
6. 结束通知后，当前状态按证据进入 idle 或 unknown；子任务仍运行时保留活动摘要，父回合完成不清除所有后台活动。
7. 长时间静默仅使新鲜度过期。对明确审批等待或长工具也保留 last_known_state，当前可信度可以降级，但绝不伪造完成/中断。
8. PID 存活只作为来源健康线索；PID 需结合启动时间防复用。进程退出不证明回合成功。

`observed` 表示该事实被直接观察，不等于当前仍新鲜。API 需同时给出 freshness、last_observed_at、reason 和 source_health。TTL 在真实长推理/长工具样本后校准，不能作为成功检测器。

### 9.4 游标、历史、乱序和故障恢复

- JSONL 按文件身份与代际增量读取；只提交完整换行记录。半行、UTF-8 分段写入、截断、同路径替换分别测试。
- 行大小、帧解压大小、半帧缓存和每源队列均设上限；超限报告 degraded 并保留最后可恢复游标，不能无限缓冲或悄悄跳过后声称数据完整。
- 文件通知只唤醒读取；补偿扫描恢复漏通知。递归目录需注册新目录，不能假定一次 watch 自动覆盖后代。
- 冷启动在捕获的文件边界内建立历史快照，静默回放；边界之后进入 live。已有游标重启后恢复状态，停机期间的旧终止事件标记 recovered，不弹出“刚完成”。
- 单一会话串行应用事件；跨来源靠原生身份关联，不只按时间戳排序。不能按“相同类型 + 同一秒”去重两个真实回合。
- 精确去重键优先原生事件 ID；文件源用文件代际 + 提交位置；跨 Hook/文件的重复终止通过会话/回合终止记录合并。
- SQLite 同一事务提交状态、游标、去重键和对外事件序号，防止崩溃导致已推进游标却丢状态。只保存最小状态元信息，事件保留设置上限。
- 缺原生关联 ID 时不能保证跨源精确一次；宁可降低通知能力，也不跨回合误合并。

### 9.5 本机 API

保留 `GET /v1/info`、`health`、`status`、`sessions`、`capabilities`、`events`。仅监听 loopback；本机状态读令牌通过当前用户受限文件分发。管理和 Hook 写入使用当前用户 ACL 的 Named Pipe / Unix Socket。

快照附 `epoch + revision`；SSE 支持按快照游标继续读取与 Last-Event-ID。历史超出保留范围明确返回 reset，再取快照。事件发布发生在数据库提交之后，慢客户端达到队列上限断开重连，不拖慢采集。最少提供一个能显示快照、订阅和断线恢复的参考客户端。

能力报告按 `(agent, surface, environment, version, source)` 返回：supported / partial / unsupported / unverified、证据级别、安装状态、健康状态和已知缺口。CLI 可用不等于桌面可用；配置成功也不等于 Hook 已触发。

### 9.6 Hooks 安装与转发

安装器执行：解析配置 → 生成差异 → 保存自身配置清单与备份 → 带并发变更检查的合并 → 原子替换 → 提示必要的信任/重载 → 等待真实事件验证。重复安装必须幂等，损坏配置必须保持原样。

卸载只删除自身仍匹配的条目；不能恢复整份旧备份而抹去用户后来添加的 Hooks。应用在升级时更改 Hook 定义须重新检测信任状态，不修改上游信任数据库。

转发器使用同一 Go 二进制的子命令：限量读 stdin、提取字段白名单、短时本机 IPC、退出。禁止输出提示词、工具参数、模型正文；监测服务不可达时正常退出，不影响 Agent 权限或工具结果。按各上游契约测试空输出/无控制字段行为，不能把一份输出格式照搬到所有 Hook。

首期无需可靠磁盘消息队列。IPC 失败允许丢失，必须通过文件补偿、来源诊断和 unknown 暴露后果，不能宣称端到端不丢事件。异步 Hook 可能乱序或在退出时被取消；终止事件是否异步应由实际平台测试决定。

## 11. 开发顺序与交付门槛

| 里程碑 | 交付 | 必须通过的验证 |
|---|---|---|
| M0：可观测性验证 | 六入口版本清单、去敏事件样本、能力报告草案 | 每入口正常请求/长工具/等待/结束/失败；确认路径与实际写入时机 |
| M1：核心纵切 | Go daemon、JSONL reader、状态机、SQLite、HTTP/SSE、Codex/Claude 文件最小链路 | 从 fixture 到 API 端到端；冷启动无历史完成通知；重启与游标事务恢复 |
| M2：原生 Hook 增强 | Claude/Codex 配置管理、IPC 转发、桌面分入口验证 | 自动审批不误报人工等待；既有 Hooks 保留；服务离线不影响 Agent |
| M3：DeepSeek 与 Pi | Zstd 完整帧/代际读取、Pi 会话树解析 | 半帧/恢复/格式版本变更；Pi 分支、无持久化、自动续跑正确降级 |
| M4：交付与稳定性 | 用户级自启动、单实例、doctor、协议文档、参考客户端、兼容清单 | 重复安装/卸载、进程异常、SSE 重连、资源与隐私验证 |

DeepSeek 的帧读取探针在 M0 就开始，不等到 M3 才发现格式障碍。M1/M2 优先形成可运行闭环；M3 补齐用户要求的四类 Agent。任一桌面入口未通过 M0，仍保留为首期必做项，不能用 CLI 结果替代后宣布全部支持。

粗略投入建议：单名熟悉 Go 和跨平台文件系统的工程师，约 5–8 人周用于实现、样本采集与首个环境验收；另预留跨平台实测资源。此为排期估算，不是交付承诺，M0 完成后根据桌面事件可达性和压缩日志测试重新估算。

## 12. 验收方案

每个样本记录产品/内核版本、OS、入口、配置模式、源格式、步骤、UI 真值时间线、采集事件、预期与实际输出。版本号必须来自实际环境，不能由文档更新时间推测。对外首次发布只列已验证版本，不写“所有版本支持”。

| 测试组 | 必测情况 | 预期 |
|---|---|---|
| 基础生命周期 | 正常请求、无工具、长工具、工具错误后继续 | 工具失败不自动变成回合失败，结束须有终止证据 |
| 审批 | 人工批准/拒绝、自动批准、并行请求、Hook 决策 | 请求与人工等待区分，解决一个请求不清空其他请求 |
| 结束 | 用户取消、API 错误、进程强杀、Stop 后续跑 | completed/interrupted/failed/unknown 不混淆 |
| 关联 | 两会话同目录、父子 Agent、并行工具、旧回合事件迟到 | 无跨会话串扰，旧结束不关闭新回合 |
| 文件 | 半行/半帧、截断、轮转、路径重建、版本迁移 | 不提交未完成记录，不重复通知，不修改上游文件 |
| 恢复 | Runtime 中途启动、重启、离线 Hook、历史扫描与新写入并发 | 历史不弹新通知；缺失可诊断；新活动不漏过扫描边界 |
| 接口 | 多客户端、断线、超出重放窗口、慢客户端 | 快照与 SSE 无竞态；显式 reset；内存有界 |
| 安装 | 已有 Hooks、并发修改、非法 JSON、未信任、卸载后用户变更 | 不覆盖用户配置，不伪报启用，不遗留无效命令 |
| 环境 | Windows 路径空格/中文、macOS/Linux、WSL/远程边界 | 单列支持结论；不能读取的源报告 unsupported/unavailable |
| 隐私 | 提示词/参数中放测试标记与模拟密钥 | Runtime DB、日志、API 和诊断包均无原文泄漏 |

硬门槛：确定性回归集零错误成功通知、零跨会话串扰、零配置覆盖；所有未知格式与丢失路径能够降级。真实环境每类状态分别报告 precision/recall、样本量和不支持项，不能用总平均值掩盖等待/中断缺口。

性能测量分两段：Agent 真实事件→源可读（上游延迟）；源可读→Runtime 发布（自身延迟）。M0 测得基线后冻结 P50/P95 目标；同时记录空闲 CPU、活跃内存、扫描读取量、Hook 耗时和队列丢弃量。首期不能把“文件已经落盘后的快速解析”宣传为 Agent 的实时性保证。

## 13. 进入实现前必须关闭的验证项

1. 六入口实际安装版本、目标 OS、数据根目录和事件样本；桌面内核版本不得用 PATH 中 CLI 版本替代。
2. Codex 新旧 rollout 格式及停止候选如何获得最终终止证据。
3. Claude 桌面 Notification/权限事件是否可达，拒绝与中断是否有独立证据。
4. DeepSeek 当前格式的完整帧、代际选择、恢复补写与结束原因映射。
5. Pi 文件模式的持久化时机与会话树分支识别；无法观察的能力明确降级。

上述项目是 M0 的工作清单，不要求用户手工完成。只有实测证明某项需求必须改变“无插件/只观察/本地执行”的范围时，再提交有证据的方案变更供决策。
