# Agent Status Runtime 软件架构设计文档

> 历史架构草案。v0.2 已将核心改为事实采集与广播，推断移至消费者；HTTP v2 与用户自助接入取代本文旧状态接口及插件管理设想。当前实现以 [v0.2 接入协议](v0.2接入协议.md) 为准。

**文档版本：** V1.0  
**文档日期：** 2026 年 10 月 22 日  
**项目定位：** 跨平台 AI Agent 状态采集、标准化与发布基础服务  
**架构状态：** 初步方案，可用于开发设计与技术评审

---

## 1. 项目定位

### 1.1 设计目标

开发一套独立运行、可被多个软件共享的 Agent 状态监测基础服务。

系统不承担 Agent 的任务执行、控制和调度，只负责观察 Agent 工作状态，并通过统一协议向本地软件、桌面界面、硬件上位机及局域网设备提供状态数据。

核心目标：

1. **独立运行：** 监测核心可作为用户级后台服务常驻，不依赖 GUI。
2. **无感监测：** 不要求用户通过监测软件启动 Agent，尽量避免额外安装 Agent 插件。
3. **统一状态：** 将不同 Agent 的事件归一化为有限的状态及通知。
4. **多端共享：** 多个软件连接同一个 Runtime，避免重复采集与配置冲突。
5. **便捷集成：** 第三方软件能够自动检测、一键安装、更新、连接 Runtime。
6. **局域网支持：** 可向其他设备提供状态查询、订阅及推送。
7. **持续扩展：** Agent 采集适配器、管理界面、第三方客户端相互独立。

### 1.2 非目标

项目第一阶段不实现：

- Agent 启动及任务调度。
- 远程批准或拒绝工具调用。
- Agent 聊天内容、推理内容的管理。
- 云端 Agent 的专有 API 接入。
- 通用插件市场或动态执行第三方代码。
- 跨互联网状态同步。
- 任意 Agent、任意版本、全部运行模式的完整兼容保证。

## 2. 总体架构

### 2.1 架构原则

采用 **独立 Runtime + 可选管理 UI + 多客户端共享** 模式。

核心服务是独立的软件交付单元。GUI、硬件上位机、第三方软件均作为 Runtime 客户端存在。

### 2.2 逻辑架构

```text
              Agent 工作环境
  ┌─────────────────────────────────┐
  │ Claude Code / Codex / OpenCode  │
  │ Pi / Qoder / Cursor / Copilot   │
  │ DeepSeek Harness / 未来 Agent   │
  └────────────────┬────────────────┘
                   │
          本地文件 / 原生 Hooks
                   │
  ┌────────────────▼────────────────┐
  │       Agent Status Runtime      │
  │                                 │
  │  ┌───────────────────────────┐  │
  │  │     Agent Adapters        │  │
  │  │  文件监听 / Hook 接收     │  │
  │  └─────────────┬─────────────┘  │
  │                │                │
  │  ┌─────────────▼─────────────┐  │
  │  │  Event Normalization      │  │
  │  │  事件标准化 / 会话关联    │  │
  │  └─────────────┬─────────────┘  │
  │                │                │
  │  ┌─────────────▼─────────────┐  │
  │  │      State Engine         │  │
  │  │  状态推导 / 可信度 / 去重 │  │
  │  └─────────────┬─────────────┘  │
  │                │                │
  │  ┌─────────────▼─────────────┐  │
  │  │       API Server          │  │
  │  │    IPC / HTTP / SSE       │  │
  │  └─────────────┬─────────────┘  │
  └────────────────┼────────────────┘
                   │
       ┌───────────┼────────────┐
       │           │            │
  官方管理 UI   硬件上位机   局域网设备
       │           │            │
  托盘/诊断    显示/控制    ESP32/移动端
```

### 2.3 核心设计约束

- Runtime 不依赖任何具体 UI 框架。
- Runtime 不依赖第三方上位机存在。
- UI 崩溃或退出，不影响状态采集。
- 客户端只能通过公开接口消费状态，不直接读取 Agent 内部文件。
- 多个客户端共享同一用户下的 Runtime 实例。
- 一个 Agent 适配器故障不应影响其他 Agent 的采集。

## 3. 软件组成与进程模型

### 3.1 组件划分

| 组件 | 主要职责 | 独立运行 |
|---|---|---|
| Agent Status Runtime | 采集、状态管理、API、数据存储 | 必须 |
| Agent Status Manager | 托盘、监测面板、配置、诊断 | 可选 |
| Runtime Bootstrapper | 安装、启动、升级、检测 Runtime | 按需 |
| Hook Receiver | 接收 Agent Hooks 并转发给 Runtime | 事件触发 |
| Client SDK | 第三方软件状态查询与订阅 | 嵌入客户端 |

Runtime 可执行文件可以同时提供 Daemon、CLI、Hook Receiver 功能，不一定需要将它们编译成多个可执行程序。

例如：

```text
agent-statusd
  ├── serve
  ├── hook
  ├── install --user
  ├── uninstall
  ├── start
  ├── stop
  ├── status --json
  └── version --json
```

上述命令是拟定的软件接口。

### 3.2 单实例原则

采用 **每个操作系统用户一个 Runtime 实例** 的模型。

该用户下安装的所有客户端共享同一个服务。

运行实例需具有：

- 用户级唯一标识。
- 单实例锁。
- 固定的本机发现机制。
- 统一状态数据库。
- 统一的 Agent Hook 管理权。

多个第三方软件同时尝试安装 Runtime 时，应通过安装锁与幂等部署避免冲突。

### 3.3 后台启动机制

| 操作系统 | 推荐方式 |
|---|---|
| Windows | 当前用户登录任务或用户级自启动 |
| macOS | LaunchAgent |
| Linux | systemd --user |

第一版采用当前用户权限，不要求管理员权限或系统级常驻服务。

默认在用户登录后启动，退出登录时停止。

## 4. Agent 数据采集架构

### 4.1 总体策略

采用两种通用采集方式：

**基础模式：本地文件增量监听**

不修改 Agent 配置，适合自动发现和低侵入监测。

**增强模式：原生生命周期 Hooks**

在用户允许的情况下自动配置，补充更直接的工具、确认、中断和结束事件。

两种采集方式可以同时启用，由状态引擎执行事件去重与可信度判断。

第一阶段不考虑 Agent 专用 SDK、ACP 或私有网络接口。

### 4.2 Agent Adapter 接口

每个 Agent 的适配器独立实现以下能力：

```text
AgentAdapter
  ├── Detect()
  ├── DiscoverSessions()
  ├── StartFileWatch()
  ├── StopFileWatch()
  ├── ParseFileEvent()
  ├── ParseHookEvent()
  ├── GetCapabilities()
  └── GetHealth()
```

适配器可只实现其中适用的能力。

它只负责发现、解析及标准化，不直接控制其他客户端的显示逻辑。

### 4.3 第一阶段适配方案

| Agent | 基础采集 | 增强采集 |
|---|---|---|
| Claude Code | JSONL | 原生 Hooks |
| Codex | JSONL | 原生 Hooks |
| OpenCode | SQLite | 暂不引入插件 |
| Pi Agent | JSONL | 暂不引入 Extension |
| Qoder IDE | Transcript JSONL | 原生 Hooks |
| Cursor IDE | 内部本地记录（辅助） | 原生 Hooks |
| VS Code Copilot | 本地会话存储（辅助） | 支持的原生 Hooks |
| DeepSeek Harness | 本地持久化事件日志 | 暂不引入桥接插件 |

该表是初始适配方向。具体路径、事件字段、运行模式和兼容版本必须在开发阶段进行实机验证。

### 4.4 文件监测模块

需要提供通用文件监测基础设施：

- 目录自动发现。
- 文件创建及变更通知。
- 增量读取偏移量管理。
- 文件轮转、截断检测。
- JSONL 不完整记录缓存。
- SQLite 只读增量查询。
- 压缩事件日志处理。
- 文件监测失效后的补偿扫描。

文件系统监测主要负责触发读取，不直接等同于 Agent 状态变化。

未检测到文件变化时，不应据此判断 Agent 已空闲或任务完成。

### 4.5 Hook 管理模块

由 Runtime 管理原生 Hook 的安装、验证与卸载。

设计要求：

- 优先使用用户级配置。
- 以合并方式修改配置。
- 不覆盖现有用户 Hooks。
- 记录自己添加的配置标识。
- 支持配置变更检测与恢复。
- Hook 不可达时不得阻断 Agent 正常执行。
- 尊重 Agent 的权限审核机制。
- 卸载时仅移除本软件所添加内容。

对于 Codex 等存在 Hook 可靠性问题的平台，应结合本地记录进行补偿，而不是将某个结束 Hook 视为绝对可信。

## 5. 统一事件与状态模型

### 5.1 核心原则

区分三个概念：

**原始事件：** Agent 或文件源实际提供的信息。

**标准化事实：** Runtime 判断已观察到的行为。

**展示状态：** 提供给第三方软件及用户的统一状态。

不能直接依靠不同 Agent 的同名 Hook 推断相同的业务含义。

### 5.2 标准化事实

第一版建议包含：

| 事实类型 | 语义 |
|---|---|
| `turn_started` | 当前 Agent 回合开始 |
| `tool_observed` | 检测到工具相关活动 |
| `tool_started` | 确认工具开始执行 |
| `tool_ended` | 工具执行结束 |
| `approval_requested` | 收到审批请求 |
| `approval_resolved` | 审批处理结束 |
| `turn_ended` | 当前回合结束 |
| `turn_interrupted` | 当前回合明确被中断 |

需要区分 `tool_observed` 和 `tool_started`，因为部分工具在真正执行之前就会发出调用前事件。

同样，审批请求不一定意味着用户真的需要操作，适配器必须保留对应的可信度和语义。

### 5.3 对外状态

主要向消费者公开五种用户关心的状态或通知：

| 业务状态 | 内部表示 | 类型 |
|---|---|---|
| 工作中 | `working` | 持续状态 |
| 调用工具 | `tool_activity` | 持续状态 |
| 等待确认 | `waiting_confirmation` | 持续状态 |
| 任务中断 | `interrupted` | 结束通知 |
| 任务完成 | `completed` | 结束通知 |

内部还需要：

- `idle`：当前回合已确认结束且没有新的活动。
- `unknown`：没有足够信息确定实时状态。
- `offline`：采集源或运行环境确认不可用。

完成、中断不应永久维持为持续状态。

结束事件到达后，系统发出通知，并按实际证据将当前会话转换为 idle 或 unknown。

### 5.4 状态可信度

每个状态或事件需携带：

- 观察来源。
- 来源事件类型。
- 事件发生时间。
- 最近有效时间。
- 是否直接观察。
- 是否为推断。
- 适配器健康状态。

建议的可信度分类：

`observed / inferred / unknown`

如果 Hook 不再触发、日志停止更新或适配器异常，状态应允许降级为 unknown。

### 5.5 多会话与事件去重

同一个 Agent 可能同时存在多个会话，不同采集器也可能报告同一事件。

统一事件必须具有：

- Agent 标识。
- 运行入口标识。
- 规范化会话 ID。
- 事件 ID。
- 事件时间。
- 数据来源。
- 事件类型。

状态引擎按会话维护状态，使用来源事件 ID、事件时间、会话关系等进行去重。

不得把两个独立会话的结束事件合并，也不能将文件历史回放当成新的任务完成通知。

## 6. Runtime 内部模块设计

### 6.1 推荐模块

| 模块 | 职责 |
|---|---|
| Adapter Registry | Agent 适配器注册、能力检测、启停 |
| Session Registry | 会话发现、关联与生命周期 |
| File Watch Manager | 本地文件和数据库增量监测 |
| Hook Manager | Hook 安装、验证、卸载、接收 |
| Event Normalizer | 将不同来源转换为标准事件 |
| State Engine | 状态推导、冲突处理、过期检测 |
| Event Dispatcher | 事件去重、排序、分发 |
| State Store | 保存最小状态与恢复数据 |
| API Server | 本地及局域网访问接口 |
| Runtime Manager | 生命周期、配置与版本管理 |

这些模块第一版可以运行在同一个 Daemon 进程内部，不需要微服务化。

### 6.2 数据存储

采用 SQLite 保存：

- 已发现的 Agent。
- 会话标识与状态快照。
- 文件增量读取游标。
- 最近事件的去重记录。
- Adapter 健康状态。
- Runtime 配置及必要元数据。

不保存完整对话、工具输入和模型输出。

实时事件可保留有限的内存队列，供 SSE 客户端重连恢复。

### 6.3 异常处理

系统需要处理：

- Agent 异常退出。
- Hook 漏发。
- 文件未及时写入。
- Agent 更新导致解析失败。
- 同时存在多个会话。
- Runtime 意外关闭或重启。
- 客户端断线或重连。

采用“**宁可报告 unknown，也不伪造 completed**”的状态原则。

## 7. 对外 API 架构

### 7.1 接口分层

Runtime 提供两个独立访问面。

**管理接口（Management API）**

用于 Runtime 的设置、Adapter 启停、Hooks 管理及诊断。

采用本机受限 IPC，不向局域网开放。

**状态接口（Status API）**

用于所有客户端获取状态。

采用本机 HTTP REST + SSE，局域网能力可选开启。

### 7.2 基础状态 API

建议第一版：

| 接口 | 功能 |
|---|---|
| `GET /v1/info` | Runtime 版本、协议版本 |
| `GET /v1/health` | 服务健康检查 |
| `GET /v1/status` | 全量状态快照 |
| `GET /v1/sessions` | 会话列表 |
| `GET /v1/capabilities` | Agent 支持能力 |
| `GET /v1/events` | SSE 事件订阅 |

接口采用版本化路径，以长期兼容第三方客户端。

### 7.3 状态数据示例

```json
{
  "schema": 1,
  "revision": 1042,
  "sessions": [
    {
      "session_id": "session-123",
      "agent": "claude-code",
      "state": "waiting_confirmation",
      "confidence": "observed",
      "source": "hook",
      "updated_at": "2026-10-22T12:00:00+08:00"
    }
  ]
}
```

### 7.4 SSE 订阅

推荐使用单向 SSE 作为首版实时推送方案。

主要事件：

- `state.changed`
- `turn.completed`
- `turn.interrupted`
- `session.discovered`
- `session.removed`
- `source.degraded`

客户端连接时先获取快照，再订阅增量事件。

每个事件具有唯一 ID 或递增序号。

断线重连时通过 `Last-Event-ID` 尝试恢复事件；超出可重放范围时重新获取快照。

必须确保状态快照与事件订阅之间不存在未处理的竞态窗口，可通过 revision 检查或带游标订阅实现。

### 7.5 不优先引入 WebSocket

首版场景以状态查询与单向通知为主，不需要双向 Agent 控制。

REST + SSE 已经可以覆盖：

- 托盘界面。
- 硬件上位机。
- 第三方桌面软件。
- 局域网状态屏。
- 普通 Web 状态页。

未来确有双向通信需求时，再增加 WebSocket，不影响原有 API。

## 8. 局域网通信架构

### 8.1 服务方式

LAN API 由 Runtime 内置提供，无需用户安装独立服务器。

默认仅监听本地地址。

用户开启局域网共享后，才绑定指定局域网接口。

### 8.2 基础能力

- HTTP 状态查询。
- SSE 实时状态订阅。
- 局域网自动发现。
- 客户端身份认证。
- 单设备访问撤销。
- 已连接客户端管理。

### 8.3 服务发现

使用可选的 mDNS/DNS-SD 广播。

拟定服务标识：

`_agentstatus._tcp.local`

第三方应用可通过服务发现定位 Runtime，无需用户手动输入 IP。

### 8.4 安全机制

推荐：

- 局域网访问默认关闭。
- LAN 服务采用 HTTPS。
- 新设备需要配对。
- 每个设备分配独立的只读凭据。
- 令牌支持撤销。
- 状态读取与管理权限分离。
- 不提供原始 Agent 会话内容。
- 不开放远程命令执行。

对于资源受限的硬件，可以使用证书固定或受限的设备接入方式，但不应直接将无认证管理接口暴露到局域网。

## 9. Runtime 安装与生命周期管理

### 9.1 产品交付形式

同一套 Runtime 支持三种交付方式。

| 交付形式 | 适用用户 |
|---|---|
| 独立 Runtime 安装包 | 无界面部署或高级用户 |
| Runtime + Manager | 需要官方管理界面的普通用户 |
| Bootstrapper / Lifecycle SDK | 硬件上位机及第三方软件 |

三种形式使用相同核心版本，不应形成互不兼容的 Runtime 分支。

### 9.2 第三方软件一键部署

例如硬件上位机启动时：

```text
上位机启动
    │
检查 Runtime
    │
    ├── 已安装并兼容
    │       └── 直接连接
    │
    ├── 已安装但未运行
    │       └── 启动服务
    │
    ├── 已安装但不兼容
    │       └── 提示升级或降级功能
    │
    └── 未安装
            └── 一键安装 Runtime
                       │
                  注册用户服务
                       │
                  启动并检查健康
                       │
                  建立状态订阅
```

一键安装应校验发布包完整性、签名和来源，并获得用户必要授权。

安装过程必须是幂等的，可重复执行而不产生多个后台实例。

### 9.3 共享 Runtime 所有权

多个软件可以依赖同一个 Runtime。

因此必须明确：

- 客户端退出不停止 Runtime。
- 客户端卸载不自动删除 Runtime。
- 客户端不能未经授权升级或卸载共享 Runtime。
- 管理操作通过受保护的本机接口执行。
- Runtime 升级必须考虑已安装客户端的协议兼容性。

不建议采用简单的“最后一个软件关闭时终止 Runtime”策略，因为客户端依赖关系不一定能够被完整识别。

### 9.4 版本体系

至少区分：

**Runtime Version**

反映核心程序、Adapter 和内部实现版本。

**Protocol Version**

反映对外状态 API 与事件格式版本。

**Adapter Version**

反映具体 Agent 适配器版本及已验证范围。

例如 Runtime 更新后，只要状态协议保持兼容，现有硬件上位机无需同步升级。

### 9.5 更新机制

推荐：

- 官方签名发布包。
- 更新前兼容性检查。
- 更新与安装过程互斥锁。
- 保留必要的回滚能力。
- 原子替换或安全安装步骤。
- 失败时恢复可运行版本。
- 兼容性问题独立诊断。

第一版可以采用用户确认更新，暂不实现后台静默更新。

## 10. 官方管理界面

### 10.1 职责

Agent Status Manager 作为可选 GUI 客户端，不直接实现采集器。

主要功能：

- 系统托盘状态。
- Agent 与会话列表。
- 实时状态显示。
- 任务完成及等待确认通知。
- Agent 适配器支持情况。
- Hook 安装与配置管理。
- Runtime 健康诊断。
- 局域网共享设置。
- 配对设备管理。
- 版本更新及卸载管理。

### 10.2 状态展示

默认只显示核心信息：

- Agent 名称。
- 会话数量。
- 当前状态。
- 状态更新时间。
- 可信度。
- 是否需要用户操作。

高级诊断界面可以显示来源事件和 Adapter 状态，但不应默认展示完整会话内容。

### 10.3 进程分离

GUI 可随时关闭或重启，不影响 Runtime。

后续可以提供其他管理实现，例如浏览器控制面板、移动管理端或第三方控制台。

## 11. 第三方软件集成

### 11.1 两套 SDK

建议逐步提供两种开发能力。

**Runtime Lifecycle SDK**

用于：

- 检测 Runtime。
- 一键安装。
- 查询版本。
- 启动服务。
- 检查健康。
- 请求升级。
- 获取连接信息。

**Status Client SDK**

用于：

- 读取 Agent 状态。
- 订阅 SSE。
- 处理重连。
- 查询会话与能力。
- 接收完成及中断事件。

第三方软件一般只需要 Status Client SDK；希望提供一键安装体验的软件，再引入 Lifecycle SDK。

### 11.2 SDK 语言策略

首版以开放 HTTP/SSE 协议为基础。

先提供协议文档和参考客户端，不必同时开发所有语言 SDK。

根据实际使用需求增加：

- TypeScript / JavaScript。
- Python。
- C#。
- Go。
- Rust 或 C ABI。

### 11.3 典型集成方式

**桌面上位机：** 自动安装 Runtime，通过本机 API 读取状态并控制 USB/串口显示设备。

**局域网硬件：** 设备配对后直接订阅 Runtime SSE。

**桌面小组件：** 订阅本机状态并显示 Agent 活动。

**第三方通知软件：** 只关注等待确认、完成、中断事件。

**Home Assistant：** 后续通过独立 MQTT 桥接实现接入。

所有客户端均不需要直接理解 Claude Code、Codex 或其他 Agent 的内部事件格式。

## 12. 推荐技术栈

| 模块 | 推荐技术 |
|---|---|
| Runtime | Go |
| 文件变化通知 | fsnotify + 补偿扫描 |
| 内部数据存储 | SQLite |
| HTTP / SSE | Go 标准 HTTP 服务 |
| 本机管理接口 | Unix Domain Socket / Windows Named Pipe |
| 官方 GUI | Tauri 或其他轻量跨平台 UI |
| LAN 自动发现 | mDNS / DNS-SD |
| 数据协议 | JSON |
| 发布与更新 | 签名二进制与平台安装包 |

选择 Go 的主要原因是跨平台编译、单文件部署、常驻后台运行和网络服务实现成本较低。

如果现有团队以 Rust 为主要技术栈，也可以采用 Rust Daemon + Tauri UI。

核心架构不应依赖具体语言或 GUI 框架。

## 14. 性能与稳定性要求

Runtime 是长期后台程序，应避免明显影响 Agent 和用户电脑的正常工作。

建议采用以下原则：

- 无活动时维持较低 CPU 占用。
- 不周期性全量解析历史文件。
- 使用有限大小的事件队列。
- 对重复文件事件进行合并。
- 对 SQLite 查询进行节流。
- 对大量并发 SSE 客户端设置连接和缓冲限制。
- 保留必要的事件游标和状态快照。
- Runtime 崩溃恢复后可以重新建立监测。
- Adapter 异常必须能够隔离和禁用。

具体 CPU、内存、延迟和准确率指标需通过实际运行数据制定，不预先承诺所有平台统一毫秒级实时监测。

## 15. 安全与隐私原则

### 15.1 最小权限

Runtime 默认以当前用户权限执行。

不需要系统级管理员权限，不要求修改 Agent 安装目录。

### 15.2 本地数据保护

监测器可能读取包含敏感内容的会话文件，但只提取状态所必需的元信息。

原则上不存储：

- 用户完整提示词。
- AI 生成内容。
- 文件正文。
- 工具参数。
- 环境变量及密钥。

### 15.3 接口安全

- Hook 上报使用受本机权限保护的 IPC。
- 本机管理接口不能被局域网访问。
- 本地 HTTP 接口也需要合理的访问控制，不能单纯依赖 localhost。
- LAN 默认关闭，开启后需认证。
- 不接受来自 LAN 的原始 Agent 状态伪造写入。
- 不允许普通状态消费者修改 Runtime 配置。

| 决策项 | 最终选择 |
|---|---|
| 产品核心 | 独立 Agent Status Runtime |
| 运行权限 | 当前用户级 |
| 运行生命周期 | 用户登录后常驻 |
| GUI | 独立、可选 |
| 第三方一键安装 | Bootstrapper / Lifecycle SDK |
| 单实例策略 | 每用户共享一个 Runtime |
| 状态采集 | 文件监听 + 可选原生 Hooks |

| 本地接口 | IPC + REST/SSE |
| 局域网接口 | 可选 HTTPS + SSE |
| 自动发现 | mDNS |
| 数据存储 | SQLite |
| 客户端权限 | 状态读取与管理分离 |
| 兼容策略 | API 版本化、能力分级、故障降级 |

## 18. 总结

本项目应定位为一项**可独立部署、可被多个软件共同使用的 AI Agent 状态基础服务**，而不仅是一个带监控面板的桌面应用。

整体采用：

**用户级 Runtime + 独立 Adapter + 统一状态引擎 + 标准 API + 可选管理 UI + 第三方一键部署能力。**

这种架构具备五个主要优势：

1. 监测核心不依赖官方 UI，也不依赖任意上位机。
2. 多个软件共享状态服务，避免重复采集和配置冲突。
3. 新增 Agent 时只需要扩展采集适配器。
4. 本地与局域网客户端可以长期使用稳定的状态协议。
5. 未来能够扩展到硬件显示、移动设备、多电脑聚合及其他自动化系统。

项目最大的持续维护成本来自第三方 Agent 的版本变化及事件可靠性，而不是 Runtime 自身的网络或状态发布功能。

因此，**架构的长期稳定边界必须放在 Runtime 的状态协议上，而不能建立在某一个 Agent 的 Hook、日志格式或内部数据库结构上。**

这应作为后续详细设计与开发实施的基本原则。
