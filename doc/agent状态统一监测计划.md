# 跨平台 AI Agent 运行状态监测系统可行性研究报告

项目性质： 本地 Agent 状态监控与局域网状态发布  
研究版本： V1.0  
研究日期： 2026 年 10 月 22 日  
研究结论： 有条件可行，建议分阶段实施

---

## 一、项目概述

### 1.1 项目背景

AI Coding Agent 正逐步从简单的对话工具发展为能够自主规划、调用工具、编辑文件、运行命令以及长期执行任务的软件工作平台。

用户可能同时运行多个 Agent，这些 Agent 分布在终端、IDE、桌面应用及不同的工作环境中。当 Agent 长时间执行任务、等待授权或结束工作时，用户通常需要切换到对应窗口才能了解其状态。

目前主流 Agent 的运行状态接口缺乏统一标准，不同平台分别采用生命周期 Hooks、插件事件、内部数据库及本地会话日志等技术机制。相关接口仍在快速迭代，第三方状态监控软件面临较高的兼容与维护成本。

本项目拟构建一个独立于 Agent 运行环境的状态监测服务，在尽可能不干扰现有工作流程的前提下，实现跨平台 Agent 状态采集、统一表达和局域网发布。

### 1.2 项目目标

支持以下八款 Agent：

1. Claude Code
2. OpenCode
3. Codex
4. Pi Agent
5. Qoder IDE
6. DeepSeek Harness
7. Cursor IDE
8. Visual Studio Code GitHub Copilot

统一对外提供以下五类状态：

 状态  定义 
------
 工作中  Agent 正在处理当前请求，但未确认进入工具执行或用户等待阶段 
 调用工具  检测到工具调用、执行或相关结果处理活动 
 等待确认  Agent 需要用户进行授权、确认或交互 
 任务中断  当前执行被明确取消或中断 
 任务完成  当前 Agent 回合明确结束 

任务中断与任务完成主要用于通知，可在界面上短暂显示；工作中、调用工具、等待确认属于实时运行状态。

系统内部另需保留“空闲、未知、离线”辅助状态，避免将无法判断的情况错误归类为任务完成。

### 1.3 用户体验要求

理想操作流程为：

1. 用户安装并启动监测软件。
2. 监测软件自动识别本地已安装的 Agent。
3. 用户继续通过原有终端或 IDE 独立使用 Agent。
4. 监测软件自动发现会话并获取状态。
5. 本机或局域网设备实时接收状态变化。

项目原则上不要求：

- 通过监测软件启动 Agent。
- 修改 Agent 程序本体。
- 给每款 Agent 手动安装独立插件。
- 修改项目源代码或工作区配置。
- 读取或向外传输完整会话内容。

允许在用户知情的情况下，由监测软件自动安装或卸载原生 Hook 配置。

需要明确的是：完整的零配置、所有状态实时准确、覆盖全部工具及运行模式，这三个目标目前无法同时保证。

## 二、技术方案研究

项目初期限定采用两种通用方案，不引入各 Agent 独有的 SDK、网络 API、ACP 或运行时管理接口。

### 2.1 方案 A：本地文件增量监听

#### 工作原理

监测软件扫描 Agent 的用户数据目录，识别会话日志、JSONL、SQLite 数据库或其他持久化事件记录。

通过文件系统变更通知与必要的低频补偿轮询，获取新增数据，并从中提取运行状态。

典型流程：

Agent 本地持久化 → 文件变化检测 → 增量读取 → 事件解析 → 状态推导

#### 优势

- 不需要额外安装 Agent 插件。
- 不需要修改 Agent 配置。
- 不要求监测软件接管 Agent 启动。
- 能够发现监测软件启动前已存在的会话记录。
- 即使 Agent 没有公开 Hook，也可能实现一定程度的状态观察。
- 对 Agent 正常执行过程的侵入性较低。

#### 局限性

- 本地持久化格式通常不是稳定的公开协议。
- Agent 可能延迟写入、批量写入，甚至仅在会话结束时保存。
- 工具调用记录可能在执行完成后才落盘。
- 授权请求与用户确认过程可能不写入会话文件。
- 文件没有新变化，不能证明 Agent 已空闲。
- 数据库结构升级可能使现有解析器失效。

因此，文件监听更适合观察“已经发生并写入记录的事件”，不一定能够准确观察“正在发生的交互状态”。

### 2.2 方案 B：原生生命周期 Hooks

#### 工作原理

监测软件为支持 Hooks 的 Agent 自动添加用户级 Hook 配置，指向监测软件自带的轻量事件转发程序。

Agent 在执行预定义生命周期节点时，调用该程序，将事件发送给监测服务。

典型流程：

Agent 生命周期事件 → 原生 Hook → 本地事件接收器 → 状态推导

#### 优势

- 事件语义通常比日志记录更明确。
- 能较及时地检测开始处理、工具活动和回合结束。
- 部分工具能直接提供权限请求和中断事件。
- 不要求用户改变 Agent 的正常启动入口。
- 原生用户级 Hooks 通常不需要安装单独插件。

#### 局限性

- 并非所有 Agent 都提供无需扩展模块的原生 Hooks。
- 各工具的 Hook 事件名称、结构和语义不同。
- 部分工具要求用户审核 Hook 或信任配置。
- 已经运行的会话不一定重新加载新 Hook 配置。
- 某些生命周期节点可能漏发或存在缺陷。
- Hook 只能报告它所观察到的事件，不能自动恢复历史状态。

Hook 必须采用非阻断式监控设计，不更改 Agent 的授权结果、工具参数或执行流程。

### 2.3 方案比较

 评价维度  文件增量监听  生命周期 Hooks 
---------
 零侵入程度  高  中高 
 无需接管启动  是  是 
 无需修改 Agent 配置  是  否 
 无需额外 Agent 插件  是  支持原生 Hook 的平台可以 
 已有会话发现  较好  较弱 
 工作状态检测  较好，受落盘影响  较好 
 工具调用检测  较好，可能延迟  较好 
 等待确认检测  普遍较弱  部分平台较好 
 中断完成检测  依赖持久化事件  依赖生命周期完整性 
 上游版本兼容成本  中高  中高 
 安全与维护风险  读取敏感历史数据  执行用户级 Hook 程序 

研究判断：两种方案互补，而非替代关系。

## 三、八款 Agent 的适配可行性

### 3.1 本地持久化基础

 Agent  主要本地数据来源  监听复杂度 
---------
 Claude Code  `~.claudeprojects` 下的会话 JSONL  低至中 
 OpenCode  本地 SQLite 会话数据库  中 
 Codex  `~.codexsessions` 下的 rollout JSONL  低至中 
 Pi Agent  `~.piagentsessions` 下的 JSONL  低 
 Qoder IDE  项目会话 transcript JSONL  低至中 
 DeepSeek Harness  持久化会话事件日志，默认压缩  中高 
 Cursor IDE  用户数据目录中的 SQLite 等内部数据  高 
 VS Code Copilot  workspaceStorage 中的会话 JSONL、数据库及索引  中高 

上述为公开资料可确认的典型路径或存储方式。不同操作系统、Agent 版本、环境变量与运行入口会影响实际路径。

特别说明：

Claude Code： 存在会话 JSONL 未在执行过程中及时写入的缺陷报告。不能只因为有 JSONL，就认定实时监控可靠。

Codex： rollout 日志适合增量读取，但某些工具记录可能在执行结束时才出现，不能保证准确表示工具开始运行的时刻。

OpenCode： 主要需要面向 SQLite 实现只读增量查询。不能把数据库文件变化等同于新增事件。

Pi Agent： JSONL 适合轻量监听，但无持久化模式无法覆盖。

DeepSeek Harness： 持久化事件具有较清楚的语义，但默认 Zstandard 压缩及批量写入增加了解码与实时读取难度。

Cursor： 本地会话结构未形成适合第三方监控的稳定公开规范，需要承担较高适配风险。

VS Code Copilot： 会话 JSONL 的存在已得到公开证据支持，但数据格式、索引和持久化位置存在版本差异。

### 3.2 文件增量监听状态覆盖

以下采用保守的工程评估口径：

- ✓：存在可直接识别相应事件的持久化依据。
- △：可部分识别或推断，但不保证准确、及时及覆盖全部路径。
- —：缺少可确认的通用、可靠依据。

 Agent  工作中  调用工具  等待确认  任务中断  任务完成 
------------------
 Claude Code  △  ✓  —  △  △ 
 OpenCode  △  ✓  △  △  △ 
 Codex  △  △  —  △  △ 
 Pi Agent  △  ✓  —  △  △ 
 Qoder IDE  △  ✓  —  △  △ 
 DeepSeek Harness  ✓  ✓  △  ✓  ✓ 
 Cursor IDE  △  △  —  △  △ 
 VS Code Copilot  △  △  —  △  △ 

✓ 仅表示能够从对应记录中找到直接证据，不代表已经验证端到端实时性。

对于工作状态，任何文件源都可能因为写入延迟而失去实时性。

对于等待确认，DeepSeek Harness 等工具虽然持久化了审批请求，但请求可能由自动策略处理，不能直接等同于用户正面对一个确认弹窗。

对于任务中断和完成，应优先使用明确的生命周期结果记录；不能通过固定时间内没有新日志来推断。

这里的“支持”限定在对应产品及运行入口，不代表云端、IDE、CLI 等所有执行模式都具备完全相同的 Hook 能力。

### 3.4 Hooks 状态覆盖评估

 Agent  工作中  调用工具  等待确认  任务中断  任务完成 
------------------
 Claude Code  ✓  ✓  ✓  △  ✓ 
 Codex  ✓  ✓  △  ✓  △ 
 Qoder IDE  ✓  ✓  ✓  △  ✓ 
 Cursor IDE  ✓  ✓  —  ✓  ✓ 
 VS Code Copilot  ✓  ✓  △  △  △

本表中的“—”对最后三款工具意味着不采用其 Plugin、Extension 或桥接接口，并非这些平台本身缺少生命周期事件。

实际重点：

Cursor： `stop` 事件包含执行结果状态，有利于区分完成、中断和错误，但缺少可覆盖全部人工审批流程的通用 Hook。

VS Code Copilot： 必须先确认正在使用的 Session Target。Copilot Harness 与旧 Local Harness 不可按相同事件结构处理；`agentStop` 也不能不经验证就等同于任务最终成功。

Claude Code 与 Qoder： 权限请求信号比较明确，但需要区分授权请求已经产生与用户当前仍在等待处理。

## 四、统一状态模型设计

### 4.1 不直接统一上游 Hook 名称

不同 Agent 对运行状态的定义不同。例如：

- 一个 `Stop` 可能只表示本轮响应停止。
- 一个工具调用前事件可能发生在人工审批之前。
- 会话文件中的最后一条消息可能仍不是任务最终结果。
- 正常结束、用户中断和模型请求失败可能具有不同记录路径。

因此，不应直接将第三方事件名称翻译成统一状态。

建议分为三层：

原始观察事件 → 标准化事实 → 对外展示状态

### 4.2 标准化事实类型

第一版只需要以下基础事实：

 事实  作用 
------
 `turn_started`  当前回合开始 
 `tool_started`  确认工具开始执行 
 `tool_ended`  工具执行结束 
 `approval_requested`  请求用户或权限系统确认 
 `approval_resolved`  确认已处理 
 `turn_ended`  当前回合结束 
 `turn_interrupted`  明确检测到执行中断 

对于无法准确识别工具开始的系统，允许上报较弱的 `tool_observed`，不能假装已经确认工具正在运行。

对于回合结束，应携带结果类型：

`completed  interrupted  failed  unknown`

“任务完成”在本项目中仅指当前 Agent 回合结束，不表示用户最初提出的业务目标已经成功实现。

### 4.3 对外状态

用户界面保持五类主要状态：

1. 工作中
2. 调用工具
3. 等待确认
4. 任务中断
5. 任务完成

内部另外维护 `idle`、`unknown` 和 `offline`。

其中：

- 等待确认具有最高展示优先级。
- 工具调用次之。
- 工作中表示仍有可信活动依据。
- 中断与完成属于带结果的一次性结束通知。
- 事件过期或数据源失效时进入未知状态。

不得把“未知”自动转成“完成”。

### 4.4 状态可信度

每个状态应同时记录：

- Observed： 直接事件证据。
- Inferred： 根据间接事件推断。
- Unknown： 当前没有足够依据。

还应记录来源、时间、会话标识和适配器健康状态。

这样某个平台 Hook 失效时，系统仍能使用文件观察结果，但应降低展示可信度。

### 4.5 多会话处理

同一 Agent 可能同时运行多个终端会话、IDE 窗口、子 Agent 或后台任务。

状态聚合器必须按会话单独维护状态，不能仅用进程名称或 Agent 品牌识别任务。

第一版建议以主会话为展示单位，子 Agent 活动合并到所属主会话，但保留其内部关联标识。

## 五、系统技术架构

### 5.1 总体结构

第一层：数据采集

- JSONL 增量监听器
- SQLite 只读查询适配器
- 压缩事件日志读取器
- 原生 Hook 事件接收器

第二层：Agent 适配器

负责本地路径发现、版本兼容、事件解析和标准化。

每个 Agent 的适配逻辑独立维护，避免上游格式变化影响其他工具。

第三层：状态聚合服务

负责：

- 会话识别与生命周期管理
- 多来源事件去重
- 状态可信度评估
- 事件失效检测
- 中断与完成通知
- 多会话状态管理

第四层：统一状态发布

建议提供：

- 本机 IPC 接口，用于 Hook 上报。
- HTTP 接口，用于获取当前状态快照。
- SSE 接口，用于订阅增量状态更新。

局域网发布应默认关闭，由用户主动开启。

第一版不需要实现远程授权、远程执行命令或任务控制。

### 5.2 增量文件监测设计

对于 JSONL：

- 根据文件身份、长度及读取偏移增量处理。
- 识别新增、截断、轮转和重建。
- 缓存未写完的最后一行。
- 监控新会话文件的创建。
- 保留最小必要的增量读取游标。

对于 SQLite：

- 使用只读连接与一致性读取方式。
- 尽可能基于事件主键、序号或更新时间增量查询。
- 处理 WAL 写入模式与多进程访问。
- 不修改第三方数据库。

对于压缩日志：

- 根据上游物理格式实现完整帧读取。
- 区分已提交事件与未完成写入。
- 不将批量写入延迟误判为 Agent 暂停。

监测软件启动时先建立会话状态快照，再处理新增事件。初次扫描历史文件时，不应将历史完成记录重新发送为新的完成通知。

### 5.3 Hooks 自动配置设计

监测软件自动发现受支持 Agent 的用户级配置目录，采用可回滚的配置修改方式。

安装过程应包括：

1. 检查当前配置是否存在。
2. 验证配置格式。
3. 备份或保存待修改配置项。
4. 以合并方式添加 Hook，不覆盖其他 Hooks。
5. 指向监测软件自带的事件转发程序。
6. 验证 Hook 是否真正触发。
7. 如需要，明确提示用户完成信任审核或重载。

Hook 处理程序应尽量短小、非阻断、具备超时保护，监测服务不可达时不应使 Agent 正常任务失败。

软件卸载时，应只撤销自身创建的配置项。

Codex 的 Hook 信任机制必须遵守，不能通过绕过信任检查来实现所谓零点击安装。

## 六、无感使用的可行性

### 6.1 无感程度分级

建议将产品支持程度分为三个级别。

 级别  定义  适用范围 
---------
 L0 纯被动  不修改 Agent 配置，仅读取已持久化数据  八款工具均可研究，覆盖能力不同 
 L1 自动配置  软件自动添加原生 Hooks，不要求用户手动编写  Claude Code、Codex、Qoder、Cursor、VS Code Copilot 
 L2 需要交互  用户需要信任 Hook、重启或执行一次设置操作  Codex 及部分版本运行模式 

本项目首期只提供 L0 与 L1，L2 作为不可避免时的安装引导，不增加独立 Agent 插件。

### 6.2 已运行会话的问题

监测软件安装时，Agent 可能已经在执行任务。

文件方案可以读取已经存在且已经持久化的记录，但不能保证还原当前真实的运行状态。

Hooks 方案也无法重放安装前的生命周期事件，除非运行中的 Agent 支持动态加载配置并且后续继续产生事件。

因此，“安装完成即可发现已有会话”与“安装完成即可准确得知已有会话的全部实时状态”应当作为两个不同的产品指标。

### 6.3 严格零修改模式的限制

如果用户要求：

- 不修改配置
- 不使用插件
- 不要求重新启动 Agent
- 不接管运行方式

那么只能依赖文件观察。

这种模式可以作为默认功能，但不应承诺所有平台的等待确认、中断及完成事件都能可靠获取。

---

## 七、技术风险分析

 风险  严重度  应对策略 
---------
 上游日志结构变更  高  独立适配器、版本检测、样例回归测试 
 Hook 生命周期事件漏发  高  文件补偿、事件健康检查、状态过期 
 授权事件语义不一致  高  区分确认请求与真实人工等待 
 会话记录延迟落盘  高  标识数据新鲜度，不以无变化推断空闲 
 插件或 Hook 运行模式差异  中高  按 CLI、IDE、Desktop 等入口分别声明能力 
 多会话关联错误  中高  会话 ID、进程与来源多重关联 
 本地数据库锁及版本变化  中  SQLite 只读连接、容错和版本适配 
 大型日志带来资源消耗  中  增量读取、有限缓存、背压处理 
 Hook 与原有配置冲突  中高  合并式修改、验证、可回滚 
 隐私数据暴露  高  本机解析、最小字段、默认禁用 LAN 
 长期维护成本增加  高  能力分级、独立升级、自动化兼容测试 

### 7.1 最大技术风险

最大的风险不是状态广播，而是事件源的可观测性和稳定性。

当 Agent 没有报告状态变化，也没有及时写入文件时，外部程序可能根本没有足够信息判断当前情况。

例如：

- 正在等待网络响应
- 正在等待用户授权
- 模型持续推理
- Agent 已经结束但没有发出结束事件
- Agent 进程异常挂起

这些情况在某些平台上可能产生相同的外部观察结果。

这是信息不足的问题，不能仅靠提高文件监听频率解决。

### 7.2 长期兼容策略

建议每个适配器显式声明：

- 适用的 Agent 及运行入口
- 已验证版本范围
- 支持的事件与状态
- 直接观察能力和推断能力
- 事件源健康状态
- 最近一次回归测试结果

当上游更新导致适配失败时，应只影响该 Agent 的对应能力，而不影响整个监测服务。

## 八、实施路线与验证方案

### 第一阶段：文件观察基础能力

优先实现：

- Claude Code JSONL
- Codex JSONL
- Pi Agent JSONL
- Qoder transcript JSONL

同时完成统一状态模型、事件聚合器与本机状态接口。

目标是验证：不修改 Agent 配置、不接管启动入口，能否稳定发现多个会话并检测实际活动。

### 第二阶段：原生 Hooks 增强

优先实现：

- Claude Code
- Qoder IDE
- Cursor IDE
- Codex

重点测试工具调用、等待授权、回合结束、用户中断。

其中 Codex 必须专门测试已知的 `Stop` 漏发和异常路径。

### 第三阶段：复杂存储适配与 IDE 集成

增加：

- OpenCode SQLite
- DeepSeek Harness 压缩事件日志
- VS Code Copilot Hooks 与会话持久化
- Cursor 本地存储补偿

重点解决平台版本差异、会话索引及持久化一致性问题。

### 第四阶段：局域网发布

实现：

- HTTP 状态快照
- SSE 状态订阅
- 设备配对或访问令牌
- 自动发现（可选）
- 状态通知去重
- 本机和局域网访问权限隔离

建议保持接口只读。远程审批及任务控制不属于第一版范围。

### 8.1 必须执行的测试场景

每款工具至少需要覆盖：

1. 正常提交请求与开始执行
2. 工具调用成功与失败
3. 触发人工确认、批准与拒绝
4. 用户主动中断任务
5. 正常结束一个回合
6. 模型请求失败或网络异常
7. 监测软件在 Agent 已运行时启动
8. Agent 退出、恢复及会话切换
9. 两个以上会话同时运行
10. 监测软件重启、Hook 不可用及日志异常

不支持的事件应被标记为“不支持”，而不是计入成功率或错误率。

### 8.2 建议验收指标

以下为拟定工程指标，不代表已经达到。

 指标  建议验收方式 
------
 会话发现准确性  统计正确识别的会话与误识别数量 
 状态检测准确率  按每类状态分别测量 precision  recall 
 事件检测延迟  分别统计 Hooks 与文件来源的 P50  P95 
 完成通知漏报率  覆盖正常、异常、中断等结束路径 
 等待确认误报率  区分自动审批和真实人工等待 
 兼容性恢复能力  模拟 Hook 失效、文件格式改变 
 对 Agent 的性能影响  记录 CPU、内存、文件读取及 Hook 开销 
 卸载完整性  确认配置恢复、不留无效 Hook 

建议将第一版验收条件设为：

- 基础会话发现及活动监测在首批目标环境中通过测试。
- Hooks 不影响 Agent 正常执行和权限判断。
- 不将未经确认的完成事件作为准确完成通知。
- 所有不支持或失效的能力能够正确降级。
- 状态监控核心不依赖任何单一 Agent 的内部实现。

具体准确率和延迟目标应在真实样本测试后确定，而不是提前给出缺乏依据的全平台保证。

 兼容性回归测试体系  高 

### 9.2 成本结构

项目不需要采购模型推理服务，也不需要调用额外模型来判断状态，因此正常运行的边际服务成本较低。

主要投入集中在：

- 初次适配开发
- 跨系统测试
- Agent 版本变化跟踪
- 事件语义验证
- 回归测试样本维护
- Bug 修复与兼容升级

长期成本取决于支持多少 Agent、多少运行入口，以及对状态准确性的承诺程度。

结论：首次实现成本可控，但长期兼容维护将是持续性投入。

为控制成本，应避免以“支持某 Agent 全部功能”为承诺单位，而应按照状态能力和已验证版本声明支持范围。

## 十、安全性与隐私可行性

本项目无需记录用户提示词、模型推理内容、工具调用参数或文件内容。

监测软件只需在本机提取：

- Agent 类型
- 会话标识
- 事件类型
- 事件时间
- 状态及结果
- 事件可信度

但读取本地会话文件的进程技术上可能接触完整敏感信息，因此必须在实现上进行数据最小化。

建议：

- 只使用当前用户权限，不要求管理员权限。
- 不复制或持久保存完整第三方会话日志。
- 不将原始日志传入局域网状态服务。
- Hook 接收器只接收本机可信来源。
- 局域网接口默认关闭，开启后要求访问控制。
- 不开放远程命令执行及授权决策接口。
- 提供清晰的权限说明、诊断及卸载恢复功能。

按上述设计，项目在个人计算机及可信局域网中具有可接受的安全实现路径。

## 十一、综合可行性评估

 评估维度  结论 
------
 技术可行性  较高，有条件可行 
 无需接管 Agent 启动  高可行 
 零修改 Agent 配置  基础模式可行 
 五种状态全部准确监测  目前不可统一保证 
 主流平台覆盖  部分高覆盖，其余需逐项验证 
 运行开销  预计较低，需测试证实 
 本机与局域网发布  高可行 
 用户安装体验  可以做到较低操作成本 
 长期维护可行性  有条件可行，依赖持续适配 
 一次开发永久兼容  不可行 

### 11.1 是否建议立项？

建议立项，但应以“分级可信的 Agent 状态监测系统”为目标，而非“全平台完整生命周期监控系统”。

第一版应该优先提供以下价值：

- 自动发现已安装 Agent 和本地会话。
- 不接管用户现有工作方式。
- 尽可能无感地检测工作和工具活动。
- 对支持原生 Hooks 的工具增强确认、中断及完成通知。
- 明确区分可靠状态、推断状态与未知状态。
- 统一向本机和局域网设备发布最小化状态信息。

### 11.2 不建议在第一版追求的目标

- 所有 Agent 的精确人工授权等待监测。
- 所有异常路径的百分之百完成检测。
- 自动控制或远程审批 Agent。
- 完整的会话内容分析。
- 云端和本地 Agent 的统一生命周期管理。
- 全自动覆盖任意未来版本且无需维护。

这些目标会显著扩大开发工作量，却不是基本状态监测功能所必需的。

## 十二、最终研究结论

本研究认为，跨平台 AI Agent 状态监测系统在技术上具备明确的实现基础。

现有八款工具均存在一定形式的本地会话或运行记录，部分平台进一步提供原生生命周期 Hooks。

采用本地持久化增量监听作为基础方案，原生 Hooks 作为可选增强方案，可以在不要求用户改变 Agent 启动习惯的前提下，实现有实际应用价值的多 Agent 状态监控。

但项目必须正视三个限制：

第一，无法保证所有平台都公开完整且实时的状态事件。

第二，无法保证本地文件和 Hooks 在所有版本及异常路径中都可靠。

第三，无法消除第三方软件快速迭代所带来的适配维护成本。

因此，推荐建立具有状态可信度标识、适配器独立维护、事件失效检测和降级处理能力的系统。

最终建议：有条件立项，先完成文件监听与标准化状态核心，再引入原生 Hooks 增强，按实际验证结果逐步扩大五种状态的覆盖范围。

项目成功的关键，不在于监测到尽可能多的内部事件，而在于向其他软件和设备提供足够准确、能够说明信息可信程度、并且在 Agent 更新后仍能优雅降级的状态信息。
